## OCT 28 CORRECTIONS - two real defects found and fixed in deploy-stream.py

1. FALSE FAILURE ON A SUCCESSFUL DEPLOY (the serious one).
   The script's post-PUT "chat peek" fetched https://lyrahome.app/chat with NO
   User-Agent header. The edge rejects headerless requests with 403, and the fetch was
   NOT wrapped in a try - so it threw an uncaught exception on the line immediately
   after a successful PUT. A working deploy would have crashed and read to him as
   broken. Fixed: the peek now sends the UA and is wrapped so it can never abort the run.
   This is the SAME failure class as the curl bug fixed earlier today, and it survived
   that fix because it was on a different line.

2. WRONG FAULT CLAIM ABOUT /api/brain.
   DEPLOY-NOW.md, README-DEPLOY.txt and DEPLOY-START-HERE.txt all listed
   "/api/brain 404" as a live fault this PUT fixes. IT IS NOT A FAULT. Measured live
   Oct 28: POST /api/brain with the family key returns 200 and a real reply, verified
   40/40 consecutive runs. It returns 404 on GET because the route is POST-only, which
   is correct design. All three docs corrected, and the script's own check was
   strengthened from "not 404" to "200 AND the body contains a reply".

   This was the fourth scaffolding error in a week and the second one that would have
   misreported the deploy. The worker has never been the problem.

3. EDGE RULE NOW PRECISELY CHARACTERISED.
   No User-Agent header at all -> 403 (error code 1010) on every path.
   Any User-Agent -> 200. Not a Python block, not an IP block, not a curl problem.
   The script sends a normal browser UA, so no curl dependency is needed anywhere and
   the checks run on any machine with Python (incl. a clean Windows box with no curl.exe).
